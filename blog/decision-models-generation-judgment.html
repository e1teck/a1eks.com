Decision Models: The LLM API Splits Into Generation and Judgment

2026-11-12  ·  LLM AI Engineering Software Architecture Decision Models

Three vendors now sell the same new primitive: a model that returns a verdict instead of prose.

This week Google shipped the Gemini Decisions API, joining Jev and OpenAI in the decision model category. The shape is nearly identical across all three: three question types, yes/no (Jev's term for it is a Noul), choice among options, and rubric scoring.

Why this matters: a large share of production LLM calls are not generation. Moderation, ticket triage, schema matching, grading model outputs in evals. All of these are judgment, and running them through a chat model means parsing free text and hoping the format holds this time.

Adoption is already visible. At the AI Engineer conference Cloudflare showed which parts of a build failure a classifier could handle, and TypeSafe AI presented their production customers.

What I would do with any existing LLM pipeline:

  1. Audit your prompts. If the output is one of N options or a score, it is a decision, not a chat.
  2. Route those calls to a decision endpoint. Keep generation where the output is actual text.
  3. Log calibration, not just the label. A 0.52 yes should be treated very differently from a 0.99 yes.
  4. Combine with routing: decisions stay cheap and fast, generation escalates to a flagship model.

My honest take: the chat completion API is splitting into generation and judgment. Most pipelines get simpler the moment judgment stops being a prompt engineering problem.
